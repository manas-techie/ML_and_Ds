 1. THE BIG PICTURE: FROM CODE TO EXECUTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Many people think Python is purely an interpreted language. It's actually both
compiled and interpreted.

FLOW:  Source Code (.py)  →  Compiler  →  Bytecode (.pyc)  →  PVM  →  CPU

1. Source Code (.py):
   The code you write.

2. Compilation (Hidden Step):
   - Python checks for syntax errors.
   - It translates your human-readable code into "Bytecode".
   - Bytecode is a low-level, platform-independent set of instructions.
   - This is stored in `__pycache__` folders (as .pyc files) to speed up
     future runs.

3. Python Virtual Machine (PVM):
   - This is the "Engine" of Python.
   - It is a software loop that iterates through the Bytecode instructions.
   - It translates Bytecode into machine code (0s and 1s) that your specific
     CPU understands and executes it.

 2. MEMORY MANAGEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Python handles memory automatically (unlike C/C++ where you malloc/free).

A. MEMORY STRUCTURE
   - Stack Memory: Stores static memory, function calls, and references to objects.
   - Heap Memory: Stores the actual objects (values).
     Example: `x = 10`
     - The variable `x` is in the Stack.
     - The integer object `10` is in the Heap.
     - `x` holds the memory address (reference) of `10`.

B. REFERENCE COUNTING (Primary Mechanism)
   - Python keeps track of how many variables point to an object.
   - Example:
     a = [1, 2]  (Ref count = 1)
     b = a       (Ref count = 2)
     del a       (Ref count = 1)
     del b       (Ref count = 0) -> MEMORY FREED IMMEDIATELY.

C. GARBAGE COLLECTION (Secondary Mechanism)
   - Handles "Circular References" where reference counting fails.
   - Example: Object A points to B, and B points to A. Even if you delete
     external references, their ref count is 1 (pointing to each other).
   - Python's Garbage Collector (GC) runs periodically to find and clean
     these isolated cycles.

 3. THE GLOBAL INTERPRETER LOCK (GIL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The GIL is a mutex (lock) that allows only one thread to hold control of the
Python interpreter at any one time.

WHY DOES IT EXIST?
- CPython's memory management (reference counting) is not thread-safe.
- Without the GIL, two threads could decrease a reference count simultaneously,
  deleting an object while it's still being used (causing crashes).

IMPACT:
- Single-threaded programs: No impact. Fast.
- Multi-threaded I/O-bound programs: Good. (GIL is released while waiting for I/O).
- Multi-threaded CPU-bound programs: Bad. Threads fight for the GIL, making
  it slower than a single thread due to overhead.

SOLUTION FOR CPU TASKS:
- Use `multiprocessing` instead of `threading`. Each process gets its own
  interpreter and own GIL.
